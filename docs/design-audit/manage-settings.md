# Design audit: Manage & Settings

Screens/states covered: `/manage/plans` (list + empty-state source read), `/manage/plans/:planId`
(plan detail, workout rotation list + reorder), `/manage/plans/:planId/workouts/:workoutId`
(workout slot editor, slot list + reorder), `/manage/exercises` (catalog + search),
`/settings` (Backup, Einheiten, Kalorien, Yazio placeholder). Dialogs opened and then
cancelled (Escape / no save): "Neuer Plan" (create), "Übungsplatz bearbeiten" (edit slot,
including its exercise `<select>` and alternatives picker), "Übung bearbeiten" (edit
exercise, including its delete-confirm path). No dropdown menus exist anywhere in this
scope (`grep DropdownMenu` in `src/features/manage`/`src/features/settings` — no matches),
so that item in the brief is N/A here. `/manage/exercises/:exerciseId` (named in the brief)
is not a real route — `docs/implementation-plan.md:375-378` documents this as a deliberate
decision ("the exercise editor is a `Dialog`, not a route"); confirmed against
`src/app/router.tsx:43-55`. No saves/deletes/imports/exports were performed; no sessions
created.

The prototype has no Manage/Settings screens, so per the brief this audit checks these
screens for **consistency** with the prototype's visual language (as expressed on its 3
hero screens, `design-reference/components.jsx`, and especially
`design-reference/Design System.html`'s token/component gallery — the only place a
generic "Dialog" pattern is documented at all) plus CLAUDE.md compliance (320px overflow,
48px taps, `min-w-0`, `t()`). Findings below cite existing audit IDs (`T-`/`D-`/`L-`/`P-`)
wherever the same root cause recurs here rather than re-deriving them.

Widths checked: 320px and 390px (app, same-origin iframe harness at `localhost:5173`).
Desktop not separately screenshotted for this group (no desktop-only layout differences
found; the shell is `max-w-screen-sm` everywhere as in other groups). Measurements taken
with `getBoundingClientRect`/`getComputedStyle` inside each iframe's own
`contentDocument`, per the brief's method (this session's outer browser window was
unexpectedly small for part of the audit, which made plain screenshots misleading for
pixel judgments — all overflow claims below are confirmed via direct DOM measurement
inside the 320px/390px iframes, not by eyeballing a screenshot).

## Confirmed correct (no finding)

- **List rows in Manage don't use the broken shared `Card` primitive.** `PlanListView.tsx:61-64`, `PlanDetailView.tsx:154`, `WorkoutSlotsView.tsx:160` all hand-roll `rounded-lg border border-border bg-surface shadow-elev-1` directly — i.e. the _correct_ `--radius-lg`(14px)/hairline-border/`shadow-elev-1` combination the prototype's `.wp-card`/`.ex-card` use, and that **T-03**/**D-20** flag the shared `Card` component for getting wrong elsewhere. Worth noting for whoever fixes T-03/D-20: these rows show the intended values already exist and work correctly when not routed through `Card`.
- **App-shell scroll containment holds inside Manage/Settings.** Confirmed live: only `<main>` has a non-zero `scrollHeight`/scrollable region in both `/manage/exercises` and `/settings`; the outer iframe `html`/`body` do not scroll. Matches CLAUDE.md's fixed-shell rule.
- **No horizontal overflow anywhere else in this group at 320px.** Explicitly measured (`scrollWidth`/`clientWidth` plus per-element right-edge checks) on the plan list, plan detail, workout slots list, and exercise catalog list — all clean. The overflow in this group is isolated to `SlotEditorDialog`'s `<select>` (M-01).
- **Settings' custom controls are consistently 48px-compliant**: `UnitsSection` toggle (`min-h-(--tap)`), `CaloriesSection` stepper buttons (`size-12`) and input row (`h-12`), `BackupSection`'s primary export/import buttons (`h-12`) — all measured at 48px. Settings is noticeably more disciplined about the tap-target rule than the Manage dialogs (M-06/M-07).
- **No dropdown menus exist in this scope** — nothing to check against the brief's "dropdown menus" item.

## Likely shared root causes

1. **The `<select>`-based `ExerciseSelect` doesn't actually shrink below its content width** (M-01) — the single highest-priority, highest-severity fix in this whole audit group; `min-w-0` is present but insufficient for a native `<select>`, and it can make a dialog's own Save button unreachable.
2. **The shared `Dialog` primitive was never adapted to this app's tokens**, mirroring **T-02**'s finding for `Sheet` — background token, shadow, title typography, and overlay opacity (M-02, M-03 [close-button size shares T-01's cause too], M-04, M-05, M-15) all trace back to `src/components/ui/dialog.tsx` alone; fixing it once fixes all 4 Manage editor dialogs simultaneously.
3. **No 48px step in the shared `Button` size scale** (M-06, M-07) — same root cause as **T-01**, with several previously-uncited `size-11`/`h-11` occurrences specific to this group's dialogs and buttons.
4. **A "primary-tinted overline" pattern generalized from one intentional prototype exception** (M-08) — same as **T-04/D-19/L-11**, concentrated here across 2 page headers + 3 inline "active/rotation" labels.
