# Design audit: Log (workout logging flow)

Screens/states covered: `/log` workout picker (suggested-today + full rotation list),
`/log/:sessionId` active session (fresh/unfilled draft, mid-fill, and a fully completed
past session reopened for correction), per-set weight input (custom, non-shadcn) in all
three states (empty/placeholder, focused, filled/blurred), save action, back navigation.
No exercise-alternatives/swap UI exists in either the prototype or the app, so that state
is not applicable (nothing to compare).

Widths checked: 320px and 390px (app, via same-origin iframe harness at `localhost:5173`),
plus a plain desktop tab (~1568/1528px, content capped at `max-w-screen-sm`). Prototype
checked at its native 390px phone frame only (per brief, its 320px behaviour is not a
design reference).

## Likely shared root causes

1. **Fixed-width neighbours squeeze the flexible weight input below its content's minimum
   at 320px** (L-01) — the single highest-priority fix in this group: real logged data is
   silently clipped, not just re-flowed.
2. **A "soft tint" completion treatment recurs instead of the prototype's solid/saturated
   "done" colour** (L-03, L-07) — index badge and filled-input border both use a
   translucent/neutral token where the prototype commits to a solid, high-contrast state;
   echoes D-07's dashboard finding, suggesting a systemic preference worth reviewing once
   rather than per-component.
3. **`--muted-foreground` used where the prototype specifically reaches for the dimmer
   `--subtle` tier** (L-10) — recurs on the set-row unit label, the exercise meta line, and
   the picker's exercise/set summary; a distinct token-choice habit from T-04/D-19's
   primary-vs-subtle overline issue, but the same class of mistake (reaching for a more
   prominent token than the design intends for de-emphasized text).
4. **The custom `SetRow`/`ExerciseLogCard` surfaces were built without reference to the
   prototype's pill/badge/chip conventions** (L-03's badge shape, L-04's tally chrome,
   L-08's stepper radius/tone) — each renders as a plainer, squarer, more neutral version
   of a component the prototype treats as a small distinct chip.
5. Already-documented, cross-cutting causes that also show up in this group and are not
   re-diagnosed here: **T-01** (no 48px step in `Button`'s size scale — this screen's back
   button), **T-04/D-19** (primary-tinted overline pattern — this screen's header overline
   and every picker card's overline, L-11), **T-05** (deliberate type-scale abstraction —
   does _not_ explain L-02's hero-input size/weight gap, which is larger than the "~2-6px"
   pattern T-05 covers).
